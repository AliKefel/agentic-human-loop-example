# The Tank Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the student starter kit for "The Tank" on `main`, branch it to `starter`, then build the full reference app on `solution` with one commit per spec milestone, and finally add screenshots from the solution to `starter` as mockups.

**Architecture:** Next.js App Router app. The harness is a hand-written TypeScript state machine (`lib/harness/*`) that advances one step per `POST /api/runs/[id]/advance`, persisting checkpoints to Supabase. All harness logic talks to storage through a `Repo` interface, with a Supabase implementation for the app and an in-memory implementation for tests, so the 12-pitch acceptance suite runs in Vitest without a database. A deterministic mock LLM (fixtures) makes every run reproducible.

**Tech Stack:** Next.js (latest, App Router, TS), React, Tailwind CSS v4, shadcn/ui, Recharts (via shadcn Chart), Supabase (`@supabase/supabase-js`, `@supabase/ssr`), `@anthropic-ai/sdk`, zod, Vitest, `pg` (migration script), pnpm.

**Spec:** `docs/SPEC.md`

## Global Constraints

- Package manager: **pnpm**. Node 24.
- Env var names (actual project): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL`, `ANTHROPIC_API_KEY` (optional), `NEXT_PUBLIC_MOCK_MODE`.
- `SUPABASE_SECRET_KEY` and `SUPABASE_DB_URL` are only read in server code (`import "server-only"`).
- Models: primary `claude-sonnet-5-5`, fallback `claude-haiku-4-5-20251001`.
- Mock mode on when `ANTHROPIC_API_KEY` is empty **or** `NEXT_PUBLIC_MOCK_MODE=true`.
- Config v1 values (verbatim from spec): fund_max_check $2,000,000; auto_max_amount $150,000; auto_max_equity 15; auto_min_score 7; disagreement_spread 5; partner limit $250,000; timeout 20,000 ms; retries 2 (backoff 500 → 1000 ms); budget 60,000 tokens and $0.50; max_steps 20; max replans 2; SLA approval 24h / exception 8h / escalation 4h.
- shadcn component whenever one exists; theme tokens in `app/globals.css` ("Deep Water").
- Every human action and listed system event writes `audit_log`.
- Commit messages for milestones on `solution` are exactly those in SPEC §7.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Double-clicking/racing `advance`** (two tabs open on one run) → a step must execute once; the second call gets 409 and the UI keeps polling. Test in Task 7.
2. **Acting on an already-decided approval** (stale queue drawer, second reviewer) → server returns 409 "already decided" and does not double-transition the run. Test in Task 10.
3. **Live LLM returning prose around JSON or fenced JSON** → the parser extracts the first JSON object before zod; still-invalid → `schema_fail` and retry. Test in Task 8.
4. **Cancelling a run that is mid-`advance`, or already terminal** → cancel of terminal returns 409; a step that finishes after cancel must not overwrite `cancelled` (status compare-and-set). Test in Task 9.
5. **Pitch text injection trying to set terms** (SkinSync, or a user-created pitch) → offer terms only ever come from schema-validated synthesis clamped to the ask; harness pre-scan escalates regardless of LLM output. Test in Task 8 + Task 11.

```sql
create or replace function audit_log_immutable() returns trigger language plpgsql as $$
begin
  raise exception 'audit_log is append-only (% blocked)', tg_op;
end $$;
create trigger audit_log_no_update before update or delete on audit_log
  for each row execute function audit_log_immutable();
create trigger audit_log_no_truncate before truncate on audit_log
  for each statement execute function audit_log_immutable();
```

- [ ] **Step 3: `0003_realtime_rls.sql`** — RLS on for all tables; anon may SELECT only the realtime tables (demo app with no auth — documented as a known trust tradeoff in HARNESS_SPEC_V2 template).

```sql
do $$ declare t text; begin
  foreach t in array array['users','pitches','harness_configs','runs','checkpoints','agent_calls','tool_calls','approvals','founder_messages','memories','incidents','audit_log'] loop
    execute format('alter table %I enable row level security', t);
  end loop;
  foreach t in array array['runs','checkpoints','agent_calls','approvals','incidents','audit_log'] loop
    execute format('create policy %I on %I for select to anon using (true)', t || '_anon_read', t);
    execute format('alter publication supabase_realtime add table %I', t);
  end loop;
end $$;
```

```ts
import type { Pitch } from "@/lib/types";

export type ToolName = "market_size_lookup" | "valuation_calculator" | "comparable_deals_search" | "red_flag_scanner" | "portfolio_lookup";
export const TOOL_NAMES: ToolName[] = ["market_size_lookup","valuation_calculator","comparable_deals_search","red_flag_scanner","portfolio_lookup"];
export const TOOL_DATA_SCOPE: Record<ToolName, string> = { market_size_lookup: "market", valuation_calculator: "financials", comparable_deals_search: "deals", red_flag_scanner: "financials", portfolio_lookup: "portfolio" };

export const TOOL_DEFS = [
  { name: "market_size_lookup", description: "Total addressable market, growth, and competitors for the pitch's sector.", input_schema: { type: "object", properties: {}, additionalProperties: false } },
  { name: "valuation_calculator", description: "Implied valuation, revenue multiple, burn multiple, and runway for the pitch's ask.", input_schema: { type: "object", properties: {}, additionalProperties: false } },
  { name: "comparable_deals_search", description: "Recent comparable seed deals in the same sector.", input_schema: { type: "object", properties: {}, additionalProperties: false } },
  { name: "red_flag_scanner", description: "Deterministic scan for inconsistent financials, unrealistic growth, and prompt injection.", input_schema: { type: "object", properties: {}, additionalProperties: false } },
  { name: "portfolio_lookup", description: "The fund's confidential current portfolio holdings in this sector.", input_schema: { type: "object", properties: {}, additionalProperties: false } },
] as const;

const INJECTION = /(ignore (all )?(previous|prior) instructions|system note to ai|disregard (the )?(rules|polic)|pre-?approved by)/i;
const CLAIMED_REV = /\$\s?([\d.,]+)\s?(k|m|million|thousand)?\s+(in\s+)?(annual\s+)?revenue/i;

export function scanRedFlags(p: Pitch): RedFlag[] {
  const flags: RedFlag[] = [];
  if (INJECTION.test(p.pitch_text)) flags.push({ code: "prompt_injection", severity: "high", detail: "Pitch text contains instructions aimed at AI reviewers." });
  const m = p.pitch_text.match(CLAIMED_REV);
  const claimed = p.claimed_revenue ?? (m ? Number(m[1].replace(/,/g, "")) * ({ k: 1e3, thousand: 1e3, m: 1e6, million: 1e6 } as Record<string, number>)[(m[2] ?? "").toLowerCase()] || (m ? Number(m[1].replace(/,/g, "")) : null) : null);
  if (claimed && p.revenue > 0 && claimed / p.revenue > 3) flags.push({ code: "inconsistent_financials", severity: "high", detail: `Pitch claims $${claimed.toLocaleString()} revenue; verified revenue is $${p.revenue.toLocaleString()}.` });
  if (claimed && p.revenue === 0 && claimed > 0) flags.push({ code: "inconsistent_financials", severity: "high", detail: "Pitch claims revenue but none is verified." });
  if (p.growth_pct > 250) flags.push({ code: "unrealistic_growth", severity: "medium", detail: `${p.growth_pct}% YoY growth claimed.` });
  if (p.revenue === 0) flags.push({ code: "pre_revenue", severity: "low", detail: "No verified revenue." });
  return flags;
}

export function runTool(name: ToolName, _args: Record<string, unknown>, p: Pitch): unknown {
  switch (name) {
    case "market_size_lookup": return { sector: p.sector, ...(MARKET_DATA[p.sector] ?? { tam_usd: 5e9, cagr_pct: 7, competitors: [] }) };
    case "valuation_calculator": {
      const implied_valuation = Math.round(p.ask_amount / (p.equity_offered / 100));
      return { implied_valuation, revenue_multiple: p.revenue > 0 ? +(implied_valuation / p.revenue).toFixed(2) : null, runway_months: p.monthly_burn > 0 ? Math.round(p.ask_amount / p.monthly_burn) : null, verified_revenue: p.revenue };
    }
    case "comparable_deals_search": return COMPARABLE_DEALS.filter(d => d.sector === p.sector);
    case "red_flag_scanner": return scanRedFlags(p);
    case "portfolio_lookup": return PORTFOLIO.filter(h => h.sector === p.sector);
  }
}
```

`advanceRun` algorithm:
1. `run = getRun`; if status not in WORKING → `{status:"idle", run}`.
2. If `run.step_count >= config.budgets.max_steps` → CAS update to `failed`, `error:"max_steps_exceeded"`, audit, create incident (Task 11 adds incident; in M2 just fail).
3. `t0`; execute handler for current status → `{status, patch}`; accumulate `usage` into `tokens_used`/`cost_usd`.
4. CAS `updateRun(id, { ...patch, status, step_count: step+1, tokens_used, cost_usd, completed_at: TERMINAL? now : null }, expectStep = step)`; if `null` → `{status:"conflict"}` (another advance or a cancel won).
5. `addCheckpoint({ seq: step+1, node: <old status>, state: { status, state, plan, decision, degraded }, duration_ms })`; audit `run.step` `{ from, to, duration_ms }`.
6. Handler throws unexpected error → CAS to `failed` with `error: message`, audit `run.failed`.

Cancel-safety: a cancel sets status `cancelled` **and** bumps `step_count`, so an in-flight step's CAS fails (Review Focus #4).
